# Дорожная карта новой версии AuroraOS EDM


Статус: начат основной мобильный Flutter-клиент этапа 1 в `mobile/`.
Клиентская ветка: `feature/flutter-client`, создана от `dev`.


## 1. Цель и последовательность развития

Создать новое приложение под ОС Аврора с последовательным расширением:

1. Мобильное согласование документов.
2. Подписание документов внутри приложения.
3. Веб-панель администратора.
4. Пользовательская веб-версия при подтверждённой необходимости.

Новая версия проектируется с нуля. Существующие `client/` и `server/` используются
как справочный материал по сценариям и интеграциям. Их протокол, модель хранения,
управление статусами и реализация подписи не являются основой новой архитектуры.

## 2. Предварительный технологический стек

| Компонент | Направление | Статус решения |
| --- | --- | --- |
| Мобильный клиент | Flutter для ОС Аврора | Начата основная реализация; PDF и подпись проверить в основном клиенте на устройстве |
| Нативная подпись | Собственный Flutter-плагин на C/C++, интеграция с криптопровайдером | Выбрать SDK и способ хранения ключа |
| Сервер | Go + chi (`github.com/go-chi/chi/v5`), модульный монолит | Принято как направление |
| API | HTTPS, JSON, OpenAPI | Принято как направление |
| Серверная БД | PostgreSQL | Принято как направление |
| Локальные данные | SQLite, приватный файловый кеш, постоянная очередь операций | Принято как направление |
| Веб-интерфейс | TypeScript + React или Vue | Выбрать перед веб-этапом |

По решению пользователя разработка ведётся сразу в основном клиенте `mobile/`,
без отдельных экспериментальных приложений. Проверки PDF, нативной интеграции
и RPM выполняются по мере интеграции в него; начало разработки само по себе
не подтверждает совместимость этих компонентов.

Если обязательные сценарии PDF или криптопровайдера не удаётся реализовать
приемлемо во Flutter, выбрать новый C++/QML-клиент с теми же прикладными границами
и серверным контрактом. Решение принять по результатам интеграционных проверок
перед дальнейшим расширением клиента.

Кроссплатформенность мобильного приложения — возможность, а не обещание поддержки
Android/iOS в первом выпуске. Целевая платформа первого выпуска — Аврора.

## 3. Архитектурные принципы

- UI отображает состояние и запускает сценарии; не управляет напрямую БД,
  криптопровайдером и сетевым протоколом.
- Прикладные сценарии отделены от Flutter/QML и инфраструктурных реализаций.
- Документ имеет стабильный ID; его содержимое хранится в неизменяемых версиях.
- Решение пользователя и подпись относятся к точной версии и заданию.
- Просмотр, подтверждённое ознакомление, согласование, подпись и доставка — разные факты.
- Локальная постановка действия в очередь не означает его принятие сервером.
- Сервер проверяет права на каждый объект и допустимость каждого перехода состояния.
- Повторы сетевых запросов не создают повторных бизнес-действий.
- Закрытые ключи не передаются на сервер и не экспортируются в Dart-слой.
- Сервер независимо проверяет присланную подпись и применяет политику доверия.
- Фоновые возможности ОС — дополнение: восстановление работы не зависит от
  непрерывного исполнения приложения в фоне.
- Начальная серверная архитектура — один сервис с внутренними модулями;
  дополнительные сервисы и брокер сообщений вводятся по конкретной необходимости.

### Организация серверного кода

Принято: модульный монолит с группировкой по бизнес-возможностям
(package-by-feature) и облегчённой Ports & Adapters. Модель и сценарии находятся
в корневом пакете модуля, HTTP- и PostgreSQL-адаптеры — в его дочерних пакетах.
Ядро не зависит от транспорта и БД; интерфейсы определяются у потребителя.
Общие пакеты содержат сборку зависимостей и техническую инфраструктуру.

Целевая иерархия и правила перехода — в
[`backend/ARCHITECTURE.md`](backend/ARCHITECTURE.md). Структура применяется
постепенно; выделение будущих модулей согласования и подписи выполняется
при реализации соответствующих этапов.

### Границы мобильного клиента

```text
Экраны и состояние UI
        ↓
Прикладные сценарии: просмотр, решение, подписание, синхронизация
        ↓
Модель предметной области и интерфейсы
        ↓
HTTP API / SQLite / файловый кеш / нативный плагин / API Авроры
```

### Основные сущности

| Сущность | Назначение |
| --- | --- |
| Document | Карточка и постоянный идентификатор документа |
| DocumentVersion | Неизменяемое содержимое, размер, алгоритм и значение контрольной суммы |
| Assignment | Задание пользователю по конкретной версии |
| Decision | Согласование, отклонение или подтверждение ознакомления |
| Signature | Подпись конкретной версии, формат и сведения о сертификате |
| SignatureVerification | Результат проверки, время и применённая политика |
| AuditEvent | История значимых действий |

### Начало серверной реализации

По отдельной задаче начата независимая от клиентского стека серверная часть в
`backend/`: Go + chi, конфигурация окружения, HTTP-таймауты, корректная остановка,
`GET /healthz`, единый JSON-формат ошибок и структурированные логи с ID запросов.
Подключён PostgreSQL через pgx и ограниченный пул `database/sql`; встроенные
SQL-миграции goose выполняются до запуска HTTP под advisory lock. Начальная
миграция создаёт схему `edm`; бизнес-таблицы добавляются вместе со сценариями.
`GET /readyz` проверяет доступность БД отдельно от работоспособности процесса.
Текущий технический контракт — `backend/api/openapi.json`; команды запуска,
сборки и проверок — `backend/README.md`.

Это частичное выполнение задач этапа 1; прогресс бизнес-API описан ниже.
Технические проверки этапа 0 и выбор клиента/криптопровайдера остаются открытыми.

Добавлены персональные учётные записи и сессии: закрытое создание пользователей
через `edmctl create-user`, вход по логину/паролю, текущий пользователь и выход.
Пароли хранятся как PBKDF2-HMAC-SHA256 (600 000 итераций, случайная соль),
случайные Bearer-токены — только в виде SHA-256-хешей в PostgreSQL.
Сессии действуют 24 часа, сохраняются при перезапуске и проверяются по БД
с учётом блокировки пользователя. Лимит входа общий через PostgreSQL:
10 попыток на логин за 15 минут; Redis не требуется.
Публичная регистрация, восстановление пароля и refresh-токены в этот шаг не входят.

Добавлены документы, неизменяемые версии PDF и задания на точную версию:
миграция `00003_documents.sql`, модуль `internal/documents` и PostgreSQL-запросы
с объектными правами. API возвращает свои действующие задания (с ограниченной
пагинацией), карточку документа и метаданные назначенной версии. Задание на одну
версию не даёт доступа к остальным; отмена убирает соответствующий доступ.
Чужие, отменённые и отсутствующие объекты возвращают одинаковый `404`.
Изменение и удаление версий запрещены триггером БД; соответствие версии документу
обеспечено составным внешним ключом. Контракт обновлён до 0.3.0.

Добавлен серверный файловый сценарий: `edmctl import-pdf` создаёт документ либо
новую версию существующего и назначение активному исполнителю; `assign-version`
назначает уже загруженную версию. ID операции обеспечивает безопасные повторы
и конфликты при изменении параметров/содержимого; отменённое задание не восстанавливается.
PDF ограничен 100 МиБ, проверяются заголовок и конечный маркер, вычисляется SHA-256.
Полный структурный разбор PDF и проверка ЭП этой проверкой не заменяются.

Решение для пилота: содержимое хранится в PostgreSQL блоками до 1 МиБ, а не в
отдельной файловой системе. Временная загрузка, проверка, финализация и назначение
атомарны: обрыв или ошибка откатывают незавершённые данные без отдельной очистки.
Финализированные блоки защищены триггерами от изменения, удаления и дополнения.
Это упрощает восстановление и резервное копирование пилота ценой объёма БД/WAL;
при росте объёмов способ хранения пересматривается через порт `documents.FileStore`.

`GET /api/v1/documents/{id}/versions/{versionID}/content` потоково отдаёт только
назначенную версию с проверкой сессии и объектных прав, `Range`/`If-Range`, ETag,
ограничением времени и единым форматом ошибок. После обрыва клиент должен сверить
полный размер и SHA-256. Контракт обновлён до 0.4.0; доступны проверки конкурентных
повторов, rollback загрузок, неизменяемости содержимого, диапазонов и отзыва доступа.
Полный сквозной сценарий этапа 1 остаётся открытым до мобильного клиента и офлайн-просмотра.

Добавлен workflow GitHub Actions `.github/workflows/backend.yml` на GitHub-hosted
runner `ubuntu-24.04`: форматирование, проверка зависимостей, `go vet` и тесты
с race detector и одноразовой PostgreSQL 17. После проверок собираются Linux/amd64
бинарники `api` и `edmctl`; архив и SHA-256 публикуются как артефакт на 14 дней.
Запуски — push, pull request и вручную. Развёртывание требует выбора целевой
платформы; клиентские проверки и RPM добавляются после подтверждения стека.

### Критерий завершения

Пользователь входит, получает назначенный документ, скачивает нужную версию
и открывает её после отключения сети. Другой пользователь без доступа не может
получить документ через API.

## 7. Этап 3 — подпись документов внутри приложения

### Реализация

```text
Flutter: выбор версии, сертификата и подтверждение
        ↓
Типизированный API плагина / Platform Channels
        ↓
C/C++: адаптер к SDK криптопровайдера
        ↓
Ключевой контейнер или поддерживаемый носитель
```

Для нового C++/QML-клиента применяется тот же адаптерный подход,
но без Flutter-моста. Конкретный способ повторного использования определяется SDK.

### Задачи

- [ ] Расширить нативный модуль клиента: сертификаты, профили подписи,
  начало операции, завершение, отмена и структурированные ошибки.
- [ ] Выполнять длительные операции вне UI-потока с учётом требований SDK.
- [ ] Передавать через мост идентификаторы и ссылки на подготовленные файлы,
  а не содержимое больших PDF или закрытые ключи.
- [ ] Связать просмотр и подписание с одним неизменяемым снимком содержимого,
  исключить подмену файла между подтверждением и операцией.
- [ ] Использовать предусмотренный SDK механизм PIN/подтверждения;
  исключить секреты из логов и сохраняемого состояния приложения.
- [ ] Реализовать выбранный формат: отдельно согласовать CMS/CAdES-профиль

- [ ] Сохранять результат локально до отправки, поддержать повтор передачи.
- [ ] На сервере проверять подпись, содержимое, цепочку доверия,

- [ ] Хранить результат проверки со временем и политикой;
  отличать «сформирована» от «проверена и принята».
- [ ] Проверить несколько подписантов, изменение содержимого,
  недоверенный сертификат и недоступность сервисов проверки.
- [ ] Проверить совместимость результата независимым инструментом/системой получателя.

### Если требуется подпись внутри PDF

- [ ] Выбрать библиотеку формирования PDF-подписей отдельно от просмотрщика.
- [ ] Проверить ByteRange, резервирование места, последовательные обновления
  и несколько подписей. Визуальный штамп не заменяет криптографическую подпись.
- [ ] Определить необходимость метки доверенного времени и долгосрочной проверки.

### Критерий завершения

Пользователь подписывает выбранную версию без выхода из приложения.
Сервер независимо принимает корректную подпись и отклоняет изменённое содержимое.
Отмена и ошибки не создают статус успешного подписания.
