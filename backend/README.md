# Новый Go-бэкенд

Начальный фундамент этапа 1: отдельный Go-модуль, chi, HTTP-сервер,
структурированные JSON-логи, идентификаторы запросов и единый формат ошибок.

## Требования и запуск

Go 1.26+. Все команды выполняются из `backend/`:

```sh
go mod download
go run ./cmd/api
```

По умолчанию сервер слушает `127.0.0.1:8080`:

```sh
curl -i http://127.0.0.1:8080/healthz
```

Ответ: `200`, `{"status":"ok"}`. Это проверка работоспособности HTTP-процесса,
не готовности PostgreSQL или бизнес-сценариев.

Конфигурация через окружение (образец в `.env.example`):

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `HTTP_ADDR` | `127.0.0.1:8080` | Адрес прослушивания `host:port` |
| `SHUTDOWN_TIMEOUT` | `10s` | Положительный таймаут завершения активных запросов |

`.env` автоматически не загружается. Пример переопределения:

```sh
HTTP_ADDR=127.0.0.1:8081 SHUTDOWN_TIMEOUT=15s go run ./cmd/api
```

SIGINT/SIGTERM останавливают приём соединений и дают активным запросам завершиться.
При превышении таймаута соединения закрываются, процесс завершается с ошибкой.
Для внешнего доступа используется HTTPS на reverse proxy с закрытым от внешней
сети HTTP-портом сервиса. Текущий HTTP-запуск предназначен для локальной разработки
или работы за таким proxy.

## Контракт

`api/openapi.json` — OpenAPI 3.0.3. `GET /healthz` — публичный технический маршрут.
Неизвестный путь возвращает JSON с кодом `not_found` (404), неподдерживаемый метод
известного маршрута — `method_not_allowed` (405), внутренняя ошибка —
`internal_error` (500). Пример:

```json
{
  "error": {
    "code": "not_found",
    "message": "Resource not found",
    "request_id": "request-identifier"
  }
}
```

`X-Request-ID` возвращается в заголовке каждого ответа. Логи содержат метод,
шаблон маршрута, статус и длительность; тела запросов и query string не логируются.

## Проверки и сборка

```sh
go test -race ./...
go vet ./...
go build -o ../bin/edm-api ./cmd/api
```

## Структура и следующий шаг

- `cmd/api/` — точка входа, таймауты и жизненный цикл сервера.
- `internal/config/` — чтение и проверка окружения.
- `internal/httpapi/` — маршрутизация, ошибки, журналирование запросов.
- `api/` — контракт текущих маршрутов.

Следующий серверный шаг: подключение PostgreSQL, миграции и контракт учётных
записей/сессий, затем объектные права, документы, неизменяемые версии и задания.
Схема и бизнес-модули будут добавляться по мере реализации сценариев.
Состояние общего плана — в `../ROADMAP.md`.
