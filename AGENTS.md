# AuroraOS EDM

## Проект
- Новая версия с нуля: мобильное согласование → подпись → веб-админка → пользовательский веб.
- Решения, этапы и критерии — в `ROADMAP.md`; сверяйся перед архитектурными изменениями и обновляй при изменении решений. Следующий этап начинай только по задаче.
- Предварительный стек: Flutter + нативная подпись C/C++, Go + chi, PostgreSQL, локальная SQLite. Flutter подтвердить проверкой PDF и криптопровайдера на устройстве.
- `client/application/` — старый C++/QML-клиент; `server/` — Python/WebSocket/SQLite; `presentation/` — презентация. README описывают старую реализацию.
- Старый код — справочный: не переноси его архитектуру автоматически. Удаление/архивирование — по отдельному решению. Новые каталоги создавай по мере реализации.

## Разработка
- Соблюдай локальные инструкции, стиль и лицензии. Изучи затронутый код и зависимости; меняй только необходимое, сохраняя чужие правки.
- Разделяй UI, сценарии, предметную модель и инфраструктуру; организуй по функциям без лишних абстракций. Сервер — модульный монолит.
- Документ имеет стабильный ID и неизменяемые версии; решения и подписи относятся к точной версии. Просмотр, согласование, подпись и доставка — разные действия.
- Сервер проверяет объектные права и актуальность задания. Запросы идемпотентны; локальные данные и очередь переживают перезапуск. Локальный успех не равен серверному.
- При изменении API проверяй контракт и клиентов; для схемы БД добавляй миграции. Учитывай обрывы, конфликты и восстановление операций.

## Аврора и подпись
- Проверяй библиотеки и Flutter-плагины для целевых ОС/CPU: Linux или pub.dev не подтверждают поддержку Авроры. Учитывай RPM-зависимости, `.desktop`, подпись и валидацию пакета.
- Криптопровайдер подключай нативным адаптером; не реализуй криптоалгоритмы. Ключи не экспортируй в Dart/на сервер; PIN не сохраняй и не логируй.
- Различай подпись RPM, подпись внутри приложения, CMS/CAdES и PDF-подпись. Штамп не заменяет ЭП; деморежим обозначай явно.
- Содержимое неизменно между просмотром и подписанием; сервер независимо проверяет подпись и доверие. УКЭП/PAdES/СКЗИ не заявляй без подтверждения.

## Инструменты и контекст
- Предпочитай специализированные инструменты; в shell — `rg`, структурный поиск — `sg`, если доступен. LSP — для символов и диагностики.
- При наличии `.codegraph/` сначала используй CodeGraph; индекс без запроса не создавай. Документация — Context7 или официальные источники нужных версий.
- Skills — по задаче; доступность инструментов проверяй. Используй точечный поиск и найденный контекст без повторного исследования.
- Для масштабного исследования сначала используй доступный `explore` через Task: узкая задача, выводы с путями/строками. Критичные выводы проверь; простые правки выполняй сам. При недоступности продолжай самостоятельно.

## Проверки и безопасность
- Перед правками проверь ветку и рабочее дерево. Коммиты, push, merge, деплой — только по запросу.
- Проверки бери из конфигурации/CI компонента: сначала целевые; для документации достаточно diff. Проверяй повторы, обрывы, доступ, версии, ошибки подписи и сохранения.
- Не отключай TLS-проверку; не доверяй входным путям. Не добавляй секреты, ключи, `.env`, реальные документы и БД в Git. К старому внешнему серверу без необходимости не подключайся.
- Не исправляй посторонние ошибки. Отвечай кратко по-русски: изменения, выполненные проверки, ограничения; не заявляй непроведённых проверок.
